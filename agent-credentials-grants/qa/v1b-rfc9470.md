# V1-B Blind Re-Extraction: RFC 9470 — OAuth 2.0 Step Up Authentication Challenge Protocol

Source: `spec-src/agent-credentials-grants/rfc9470.txt` only.

## 1. Error code and WWW-Authenticate parameters (§3)

**Error code:** `insufficient_user_authentication` (§3; IANA-registered in §10.1)

- Semantics: "The authentication event associated with the access token presented with the request does not meet the authentication requirements of the protected resource." (§3)
- It is a new error code value for the challenge of the Bearer authentication scheme's `error` parameter (from RFC 6750) and other OAuth authentication schemes that use the same `error` parameter (e.g., RFC 9449 DPoP) (§3).
- Usage Location per IANA registration: "resource access error response" (§10.1).

**WWW-Authenticate auth-param values defined (§3):**

| Parameter | Value semantics | § |
|---|---|---|
| `acr_values` | A space-separated string listing the authentication context class reference values **in order of preference**. The protected resource requires **one of** these values for the authentication event associated with the access token. (Authentication context per Section 1.2 of [OIDC].) | §3 |
| `max_age` | The allowable elapsed time **in seconds** since the **last active authentication event** associated with the access token (an active authentication event entails a user interacting with the authorization server in response to an authentication prompt). May be conveyed as token or quoted-string (Section 11.2 of [RFC9110]) but has to represent a **non-negative integer**. | §3 |

Notes (§3): `max_age` and `acr_values` MAY both occur in the same challenge; the resource server MAY also include the `scope` attribute (per Section 3.1 of RFC 6750) if scopes are also lacking. This spec only defines usage of these auth-params with the `insufficient_user_authentication` error code, but does not preclude future specs from using them with other error codes. Example challenges use HTTP `401 Unauthorized` (Figures 2 and 3).

## 2. Relaying the challenge into an authorization request (§4)

The client receiving a challenge carrying `insufficient_user_authentication` SHOULD parse the WWW-Authenticate header for `acr_values` and `max_age` and use them, if present, in constructing an authorization request, conveyed to the authorization server's **authorization endpoint** via the user agent (§4).

- Exact authorization request parameter names: `acr_values` and `max_age` — the same names as the challenge auth-params. Both are OPTIONAL authorization request parameters defined in Section 3.1.2.1. of [OIDC] (§4).
- RFC 9470 introduces no changes to authorization server behavior defined in [OIDC] for processing those parameters (§4).
- Examples: `...&acr_values=myACR` (Figure 4); `...&max_age=5` (Figure 5).

## 3. Token / introspection claims involved

| Claim (exact name) | Where it appears | Asserted by | Semantics | § |
|---|---|---|---|---|
| `acr` | JWT access token (per Section 2.2.1 of [RFC9068]) | Authorization server | Authentication context of the user-authentication event performed during the course of obtaining the access token; value established at user-authentication time, does not change on access token renewals | §6.1 |
| `auth_time` | JWT access token (per Section 2.2.1 of [RFC9068]) | Authorization server | Time of the user-authentication event; established at user-authentication time, unchanged by renewals | §6.1 |
| `acr` | Token introspection response, top-level member (RFC 7662) | Authorization server (in its introspection response) | "String specifying an authentication context class reference value that identifies the authentication context class that was satisfied by the user-authentication event performed." | §6.2 (IANA §10.2) |
| `auth_time` | Token introspection response, top-level member (RFC 7662) | Authorization server (in its introspection response) | "Time when the user authentication occurred. A JSON numeric value representing the number of seconds from 1970-01-01T00:00:00Z UTC until the date/time of the authentication event." | §6.2 (IANA §10.2) |
| `acr` | ID Token (per [OIDC] Section 5.5.1.1, restated) | Authorization server | Value satisfying the requested authentication context class reference; if the desired level cannot be met, a value reflecting the current session's authentication level | §5 |
| `auth_time` | ID Token (per [OIDC] Section 3.1.2.1, restated) | Authorization server | MUST be included in the issued ID Token if the request includes `max_age` | §5 |

Related (not a claim): AS metadata value `acr_values_supported` (defined in Section 3 of [OIDCDISC], carried per RFC 8414) advertises support — its presence signals the AS will understand and honor `acr_values` and `max_age` in incoming authorization requests (§7).

## 4. Capitalized BCP 14 requirements (MUST / MUST NOT / SHOULD / SHOULD NOT)

The RFC contains few normative keywords. Complete list of MUST / MUST NOT / SHOULD / SHOULD NOT occurrences (excluding the §1.1 BCP 14 boilerplate itself):

| # | Keyword | Requirement (exact substance) | § |
|---|---|---|---|
| 1 | SHOULD | "A client receiving a challenge from the resource server carrying the insufficient_user_authentication error code SHOULD parse the WWW-Authenticate header for acr_values and max_age and use them, if present, in constructing an authorization request." | §4 |
| 2 | SHOULD | (Restatement of [OIDC] Section 5.5.1.1) In case the desired authentication level cannot be met, "the authorization server SHOULD include a value reflecting the authentication level of the current session (if any) in the acr claim." | §5 |
| 3 | MUST | (Restatement of [OIDC] Section 3.1.2.1) "if a request includes the max_age parameter, the authorization server MUST include the auth_time claim in the issued ID Token." | §5 |
| 4 | SHOULD | "when it comes to access tokens in this specification, the authorization server SHOULD consider the requested acr value as necessary for successfully fulfilling the request" — i.e., include the requested acr in the access token only if the authentication operation successfully met its requirements; otherwise the authorization request fails and returns an unmet_authentication_requirements error as defined in [OIDCUAR]. | §5 |
| 5 | MUST NOT | "This document MUST NOT be used to position OAuth as an authentication protocol." | §9 |

No SHOULD NOT occurs anywhere in the RFC.

Out-of-scope for this list but present as capitalized keywords: MAY in §3 (both auth-params in one challenge; scope attribute), §5 (AS MAY attempt to satisfy requested acr, restating OIDC), §6 (other encoding/validation methods), §9 (RS MAY return a challenge without verifying a valid token); OPTIONAL in §4 (acr_values/max_age are OPTIONAL OIDC parameters). Note: §2 contains a lowercase, non-normative "must not" ("a client must not attempt to inspect the content of the access token").
