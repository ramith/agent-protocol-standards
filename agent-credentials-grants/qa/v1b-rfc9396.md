# RFC 9396 — OAuth 2.0 Rich Authorization Requests (V1-B blind re-extraction)

Source: `spec-src/agent-credentials-grants/rfc9396.txt` only.

## 1. The `authorization_details` field and its structure

The request parameter `authorization_details` contains, in JSON notation, an **array of objects**; each JSON object contains the data to specify the authorization requirements for a certain type of resource (§2). An `authorization_details` array MAY contain multiple entries of the same `type` (§2). When common data fields are used in combination within one object, the permissions requested are the **product** of all the values (all `actions` at all `locations` for all `datatypes`); finer control requires multiple objects (§2.2).

| Field | Type | Meaning | § ref |
|---|---|---|---|
| `type` | string | REQUIRED identifier for the authorization details type; its value determines the allowable contents of the object that contains it, and is unique for the described API in the context of the AS. The AS controls its interpretation and the fields it allows; collision-resistant (e.g., URI) values are RECOMMENDED for cross-server APIs. | §2, §2.1 |
| `locations` | array of strings | Location of the resource or RS, typically URIs identifying the location of the RS; lets a client specify a particular RS (audience restriction). | §2.2 |
| `actions` | array of strings | The kinds of actions to be taken at the resource. | §2.2 |
| `datatypes` | array of strings | The kinds of data being requested from the resource. | §2.2 |
| `identifier` | string | A string identifier indicating a specific resource available at the API. | §2.2 |
| `privileges` | array of strings | The types or levels of privilege being requested at the resource. | §2.2 |

Use of the common fields by an API definition is not required; they are reusable generic components, and an API MAY define its own extension fields subject to the object's `type`. Allowable values of all fields are determined by the API being protected, as defined by a particular `type` value (§2.2).

## 2. Where `authorization_details` can appear in protocol messages

- **Authorization request** — usable wherever `scope` is used for the same purpose: authorization requests per RFC 6749 (form-urlencoded serialized JSON), device authorization requests per RFC 8628, and backchannel authentication requests per OID-CIBA (§3). Implementers MAY use pushed authorization requests (RFC 9126) and should consider `request_uri`/request objects (RFC 9101) for large or integrity-protected requests (§3, §11.4, §12).
- **Authorization response** — NOT extended: "This specification does not define extensions to the authorization response" (§4).
- **Token request** — parameter specifying the authorization details the client wants the AS to assign to an access token (§6).
- **Token response** — the AS MUST return the `authorization_details` as granted by the resource owner and assigned to the respective access token; it MAY be enriched by the AS relative to the request (§7, §7.1).
- **JWT-based access token** — as a top-level claim (RECOMMENDED, filtered to the specific audience) (§9.1; IANA registration §14.2).
- **Token introspection response** — as a top-level member of the introspection response JSON object, with the same structure defined in §2, potentially filtered/extended for the requesting RS (§9.2; IANA registration §14.3).
- IANA "OAuth Parameters" registration lists usage locations: authorization request, token request, token response (§14.1). The error `invalid_authorization_details` is registered for the token endpoint and authorization endpoint (§14.6).

## 4. The 8 most load-bearing requirements

| # | Requirement | Obligated party | § ref |
|---|---|---|---|
| 1 | The `type` field is REQUIRED in every authorization details object; its value determines the allowable contents of the object. | Client (to send); AS rejects objects missing required fields per §5 | §2 |
| 2 | The AS MUST refuse to process any unknown authorization details type or authorization details not conforming to the respective type definition, and MUST abort processing and respond with error `invalid_authorization_details` if any object contains an unknown type value, unknown fields, fields of the wrong type, fields with invalid values, or is missing required fields. (The Token Error Response MUST conform to the same rules, §8.) | AS | §5 (§8) |
| 3 | When `authorization_details` and `scope` are used together, the AS MUST process both sets of requirements in combination with each other for the given authorization request. | AS | §3.1 |
| 4 | When gathering user consent, the AS MUST present the merged set of requirements represented by the authorization request. | AS | §3.1 |
| 5 | In the token response, the AS MUST return the `authorization_details` as granted by the resource owner and assigned to the respective access token (it MAY omit values to the client). | AS | §7 |
| 6 | In order to enable the RS to enforce the authorization details as approved in the authorization process, the AS MUST make this data available to the RS (e.g., JWT access token claim or introspection; if included in introspection, it MUST be a top-level `authorization_details` member with the §2 structure, per §9.2; adding it as a top-level JWT claim, filtered to the specific audience, is RECOMMENDED, per §9.1). | AS (making data available); the RS performs the runtime enforcement | §9 (§9.1, §9.2) |
| 7 | If the integrity of the `authorization_details` is a concern, clients MUST protect `authorization_details` against tampering and swapping (signed request objects per RFC 9101, or `request_uri` per RFC 9101 with RFC 9126). | Client | §12 |
| 8 | The AS MUST properly sanitize and handle the data passed in the `authorization_details` in order to prevent injection attacks. | AS | §12 |

**Who bears the enforcement obligation, per the spec:** the AS and the respective RS "will together enforce this consent" (§1). Concretely, the AS bears the obligations to validate/refuse requests (§5, §8), check that the underlying grant or client policy (for `client_credentials`) allows issuance at the token endpoint — otherwise refusing with `invalid_authorization_details` (§6) — gather consent (§3.1), issue and return granted details (§7), and make the approved details available to the RS (§9); the RS enforces the authorization details (or token data derived from them) at the protected API, enabled by that AS-provided data (§9, §11.1).

Runner-up RECOMMENDED items: a given API should use only one form of requirement specification (`scope` vs `authorization_details`) (§3.1); API designers should choose unambiguous, collision-resistant `type` values (§2.1).
