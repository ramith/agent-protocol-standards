# V1-B Blind Re-extraction: RFC 8707 — Resource Indicators for OAuth 2.0

Source: `/Users/ramith/code/agent-protocol-standards/spec-src/agent-credentials-grants/rfc8707.txt` (RFC 8707, February 2020). All quotes verbatim; § refs are to RFC 8707 unless noted.

## 1. Syntactic constraints on the `resource` parameter value

Capitalized BCP 14 constraints (all in §2, from the `resource` parameter definition unless noted):

- **MUST — absolute URI** (§2): "Its value MUST be an absolute URI, as specified by Section 4.3 of [RFC3986]."
- **MUST NOT — fragment** (§2): "The URI MUST NOT include a fragment component."
- **SHOULD NOT — query** (§2): "It SHOULD NOT include a query component, but it is recognized that there are cases that make a query component a useful and necessary part of the resource parameter, such as when one or more query parameters are used to scope requests to an application."
- **MAY — locator** (§2): "The \"resource\" parameter URI value is an identifier representing the identity of the resource, which MAY be a locator that corresponds to a network-addressable location where the target resource is hosted."
- **SHOULD — most specific URI** (§2, value-selection guidance rather than pure syntax): "The client SHOULD provide the most specific URI that it can for the complete API or set of resources it intends to access."
- **SHOULD — base URI** (§2, value-selection guidance): "The client SHOULD use the base URI of the API as the \"resource\" parameter value unless specific knowledge of the resource dictates otherwise."

Lowercase prose (non-BCP-14) about the value:

- §2: "The parameter can carry the location of a protected resource, typically as an https URL or a more abstract identifier."
- §2.1 (representation in JWT-secured requests): "For an authorization request sent as a JSON Web Token (JWT), such as when using the JWT Secured Authorization Request [JWT-SAR], a single \"resource\" parameter value is represented as a JSON string while multiple values are represented as an array of strings."
- §3 (Security Considerations): "Whenever feasible, the \"resource\" parameter should correspond to the network-addressable location of the protected resource." (lowercase "should")
- §3 (multi-tenant hosts): "it is important to use a specific resource URI including any portion of the URI that identifies the tenant, such as a path component."
- §3 (abstract identifiers): "If the \"resource\" parameter contains an abstract identifier, it is the client's responsibility to validate out of band that any network endpoint to which tokens are sent are the intended audience for that identifier."

## 2. Where the parameter may appear; multiple-occurrence semantics

Where it may appear:

- §2 (capitalized MAY): "In requests to the authorization server, a client MAY indicate the protected resource (a.k.a. resource server, application, API, etc.) to which it is requesting access by including the following parameter in the request."
- §2.1 — authorization request to the authorization endpoint. Effect differs by flow (lowercase prose): in the implicit flow "the requested resource is applicable to that access token"; in the code flow "the requested resource is applicable to the full authorization grant."
- §2.2 — access token request to the token endpoint, "for all grant types": "When the \"resource\" parameter is used on an access token request made to the token endpoint, for all grant types, it indicates the target service or protected resource where the client intends to use the requested access token."
- §5.1 (IANA registration, non-normative confirmation): "Parameter usage location: authorization request, token request".

Multiple occurrence:

- §2 (capitalized MAY): "Multiple \"resource\" parameters MAY be used to indicate that the requested token is intended to be used at multiple resources."
- §2.1 (lowercase, JWT-secured request): multiple values "are represented as an array of strings" (full quote in item 1).
- §2.2 (lowercase, combined semantics with scope): "The semantics of such a request are that the client is asking for a token with the requested scope that is usable at all the requested target services. Effectively, the requested access rights of the token are the cartesian product of all the scopes at all the target services."
- §3 (lowercase, discouragement): "Although multiple occurrences of the \"resource\" parameter may be included in a token request, using only a single \"resource\" parameter is encouraged." Also §3: "a high degree of trust between the involved parties is needed when using access tokens with multiple audiences" and "an authorization server may be unwilling or unable to fulfill a token request with multiple resources."

Omission (§2.1, capitalized MAYs — see item 5): the authorization server MAY process a request lacking the parameter with no specific resource or a predefined default, MAY require clients to specify resource(s), and MAY fail requests that omit it with an "invalid_target" error.

## 3. Error code for an unacceptable resource

Error code: `invalid_target`.

Definition sentence (§2): "The requested resource is invalid, missing, unknown, or malformed."

Surrounding prose (§2, lowercase): "The following error code is provided for an authorization server to indicate problems with the requested resource(s) in response to an authorization request or access token request. It can also be used to inform the client that it has requested an invalid combination of resource and scope."

Usage on rejection (§2.1 — note lowercase "should", not a capitalized requirement): "If the authorization server fails to parse the provided value(s) or does not consider the resource(s) acceptable, it should reject the request with an error response using the error code \"invalid_target\" as the value of the \"error\" parameter and can provide additional information regarding the reasons for the error using the \"error_description\"."

IANA registration (§5.2): Error name `invalid_target`; "Error usage location: implicit grant error response, token error response"; "Related protocol extension: resource parameter".

## 4. Audience representation in the issued token

The RFC does not mandate any representation of the audience in the issued token, and does not even mandate audience restriction itself:

- The only normative statement is a SHOULD, not a MUST (§2): "The authorization server SHOULD audience-restrict issued access tokens to the resource(s) indicated by the \"resource\" parameter."
- Representation is stated only as a possibility, in lowercase prose (§2): "Audience restrictions can be communicated in JSON Web Tokens [RFC7519] with the \"aud\" claim and the top-level member of the same name provides the audience restriction information in a Token Introspection [RFC7662] response." — "can be communicated", not a requirement; JWT and introspection are cited as vehicles, no token format or claim is required.
- The audience value need not equal the parameter value (§2, lowercase "may"): "The authorization server may use the exact \"resource\" value as the audience or it may map from that value to a more general URI or abstract identifier for the given resource."
- The examples in Figures 4 and 6 (§2.2) show JWT access tokens whose decoded "aud" equals the exact requested resource ("https://cal.example.com/", "https://contacts.example.com/"), but these are non-normative examples.

## 5. Complete list of capitalized BCP 14 requirements

(Excluding the §1.1 boilerplate defining the key words.)

1. §2 — "a client MAY indicate the protected resource (a.k.a. resource server, application, API, etc.) to which it is requesting access by including the following parameter in the request."
2. §2 — "Its value MUST be an absolute URI, as specified by Section 4.3 of [RFC3986]."
3. §2 — "The URI MUST NOT include a fragment component."
4. §2 — "It SHOULD NOT include a query component..."
5. §2 — "...which MAY be a locator that corresponds to a network-addressable location where the target resource is hosted."
6. §2 — "Multiple \"resource\" parameters MAY be used to indicate that the requested token is intended to be used at multiple resources."
7. §2 — "The client SHOULD provide the most specific URI that it can for the complete API or set of resources it intends to access."

9. §2 — "The authorization server SHOULD audience-restrict issued access tokens to the resource(s) indicated by the \"resource\" parameter."
10. §2.1 — "If the client omits the \"resource\" parameter when requesting authorization, the authorization server MAY process the request with no specific resource or by using a predefined default resource value."

12. §2.1 — "...and MAY fail requests that omit the parameter with an \"invalid_target\" error." (second MAY of the same sentence)

Total: 12 capitalized keyword instances (1 MUST, 1 MUST NOT, 1 SHOULD NOT, 4 SHOULD, 5 MAY). §2.2, §3, and §4 contain no capitalized BCP 14 keywords — notable lowercase near-requirements there include "the authorization server should downscope the scope value" (§2.2), "the authorization server must indicate the access token's effective scope to the client in the \"scope\" response parameter value when it differs from the scope requested by the client" (§2.2, lowercase, restating Section 5.1 of [RFC6749]), and "using only a single \"resource\" parameter is encouraged" (§3).
