# RFC 8693 (OAuth 2.0 Token Exchange) — Blind Re-Extraction (V1-B)

Source: `spec-src/agent-credentials-grants/rfc8693.txt` only.

## 1. Token Exchange Request Parameters (§2.1)

| Parameter | Required/Optional (as stated) | Meaning | § |
|---|---|---|---|
| `grant_type` | REQUIRED | The value `urn:ietf:params:oauth:grant-type:token-exchange` indicates that a token exchange is being performed. | §2.1 |
| `resource` | OPTIONAL | A URI that indicates the target service or resource where the client intends to use the requested security token; MUST be an absolute URI, MAY include a query component, MUST NOT include a fragment component; may be repeated for multiple resources. | §2.1 |
| `audience` | OPTIONAL | The logical name of the target service where the client intends to use the requested security token; may be repeated, and may be combined with `resource`. | §2.1 |
| `scope` | OPTIONAL | A list of space-delimited, case-sensitive strings specifying the desired scope of the requested security token in the context of the service or resource where the token will be used. | §2.1 |
| `requested_token_type` | OPTIONAL | An identifier (per §3) for the type of the requested security token; if unspecified, the issued token type is at the discretion of the authorization server. | §2.1 |
| `subject_token` | REQUIRED | A security token that represents the identity of the party on behalf of whom the request is being made; typically its subject will be the subject of the issued token. | §2.1 |
| `subject_token_type` | REQUIRED | An identifier (per §3) that indicates the type of the security token in the `subject_token` parameter. | §2.1 |
| `actor_token` | OPTIONAL | A security token that represents the identity of the acting party — typically the party authorized to use the requested security token and act on behalf of the subject. | §2.1 |
| `actor_token_type` | REQUIRED when `actor_token` is present in the request but MUST NOT be included otherwise | An identifier (per §3) that indicates the type of the security token in the `actor_token` parameter. | §2.1 |

## 2. Successful Response Parameters (§2.2.1)

| Parameter | Required/Optional (as stated) | Meaning | § |
|---|---|---|---|
| `access_token` | REQUIRED | The security token issued by the authorization server in response to the token exchange request; the name `access_token` is used for historical reasons and the issued token need not be an OAuth access token. | §2.2.1 |
| `issued_token_type` | REQUIRED | An identifier (per §3) for the representation of the issued security token. | §2.2.1 |
| `token_type` | REQUIRED | A case-insensitive value specifying the method of using the access token issued (e.g., `Bearer`); the value `N_A` is used if the issued token is not an access token or usable as an access token. | §2.2.1 |
| `expires_in` | RECOMMENDED | The validity lifetime, in seconds, of the token issued by the authorization server. | §2.2.1 |
| `scope` | OPTIONAL if the scope of the issued security token is identical to the scope requested by the client; otherwise, it is REQUIRED | The scope of the issued security token. | §2.2.1 |
| `refresh_token` | OPTIONAL | A refresh token; typically not issued when exchanging one temporary credential for another, but can be issued where the client needs access even when the original credential is no longer valid (e.g., offline scenarios). | §2.2.1 |

## 3. Token Type Identifier URIs (§3)

| URI | Indicates | § |
|---|---|---|
| `urn:ietf:params:oauth:token-type:access_token` | The token is an OAuth 2.0 access token issued by the given authorization server. | §3 |
| `urn:ietf:params:oauth:token-type:refresh_token` | The token is an OAuth 2.0 refresh token issued by the given authorization server. | §3 |
| `urn:ietf:params:oauth:token-type:id_token` | The token is an ID Token as defined in Section 2 of [OpenID.Core]. | §3 |
| `urn:ietf:params:oauth:token-type:saml1` | The token is a base64url-encoded SAML 1.1 assertion. | §3 |
| `urn:ietf:params:oauth:token-type:saml2` | The token is a base64url-encoded SAML 2.0 assertion. | §3 |
| `urn:ietf:params:oauth:token-type:jwt` | The token is a JWT (this value is defined in Section 9 of [JWT], not by RFC 8693 itself). | §3 |

Other URIs MAY be used to indicate other token types (§3).

## 4. Claims Defined by RFC 8693 (§4.x)

| Claim | Where it may appear | Semantics | § |
|---|---|---|---|
| `act` (Actor) | JWT Claims Set; also as a top-level member of an OAuth token introspection response (same semantics and format) | Expresses within a JWT that delegation has occurred and identifies the acting party to whom authority has been delegated; the value is a JSON object whose members are claims that identify the actor (non-identity claims such as `exp`, `nbf`, `aud` are not used within it). | §4.1 |
| `scope` (Scopes) | JWT Claims Set (RFC 7662 introspection already defines the `scope` parameter) | A JSON string containing a space-separated list of scopes associated with the token, in the format of Section 3.3 of RFC 6749. | §4.2 |
| `client_id` (Client Identifier) | JWT Claims Set (RFC 7662 introspection already defines the `client_id` parameter) | Carries the client identifier of the OAuth 2.0 client that requested the token. | §4.3 |
| `may_act` (Authorized Actor) | JWT Claims Set; also as a top-level member of an OAuth token introspection response (same semantics and format) | Makes a statement that one party is authorized to become the actor and act on behalf of another party; the value is a JSON object whose members are claims identifying the party asserted as eligible to act for the party identified by the JWT containing the claim. | §4.4 |

### `act` nesting rule and access-control role of nested members (§4.1)

- Nesting rule (spec's wording): a chain of delegation can be expressed by nesting one `act` claim within another — "The outermost 'act' claim represents the current actor while nested 'act' claims represent prior actors", and the least recent actor is the most deeply nested.
- Access control: "For the purpose of applying access control policy, the consumer of a token MUST only consider the token's top-level claims and the party identified as the current actor by the 'act' claim. Prior actors identified by any nested 'act' claims are informational only and are not to be considered in access control decisions."

## 5. Eight Most Load-Bearing MUST / MUST NOT Requirements

1. In processing the request, the authorization server MUST perform the appropriate validation procedures for the indicated token type and, if the actor token is present, also perform the appropriate validation procedures for its indicated token type. (§2.1)
2. The value of the `resource` parameter MUST be an absolute URI, as specified by Section 4.3 of [RFC3986], that MAY include a query component and MUST NOT include a fragment component. (§2.1)
3. `actor_token_type` is REQUIRED when the `actor_token` parameter is present in the request but MUST NOT be included otherwise. (§2.1)
4. If the request itself is not valid or if either the `subject_token` or `actor_token` are invalid for any reason, or are unacceptable based on policy, the authorization server MUST construct an error response, as specified in Section 5.2 of [RFC6749]. (§2.2.2)
5. In that error response, the value of the `error` parameter MUST be the `invalid_request` error code. (§2.2.2)
6. For the purpose of applying access control policy, the consumer of a token MUST only consider the token's top-level claims and the party identified as the current actor by the `act` claim; prior actors in nested `act` claims are informational only and are not to be considered in access control decisions. (§4.1)
7. Tokens employed in this context may contain privacy-sensitive information and MUST only be transmitted over encrypted channels, such as Transport Layer Security (TLS). (§6)
8. In cases where it is desirable to prevent disclosure of certain information to the client, the token MUST be encrypted to its intended recipient. (§6)
