# RFC 9449 — OAuth 2.0 Demonstrating Proof of Possession (DPoP): Blind Re-Extraction (V1-B)

Source: `spec-src/agent-credentials-grants/rfc9449.txt` (RFC 9449, September 2023) only.

## 1. DPoP Proof JWT JOSE Header Fields (§4.2)

The JOSE Header of a DPoP JWT MUST contain at least the following parameters:

| Header field | Value / requirement |
|---|---|
| `typ` | Exact value `dpop+jwt` — explicitly types the DPoP proof JWT (per Section 3.11 of RFC 8725). |
| `alg` | Identifier for a JWS asymmetric digital signature algorithm from [IANA.JOSE.ALGS]. MUST NOT be `none` or an identifier for a symmetric algorithm (MAC). |
| `jwk` | The public key chosen by the client, in JWK (RFC 7517) format as defined in Section 4.1.3 of RFC 7515. MUST NOT contain a private key. |

## 2. DPoP Proof JWT Payload Claims (§4.2)

| Claim | Required? | Meaning (one line) |
|---|---|---|
| `jti` | Required (always) | Unique identifier for the DPoP proof JWT (negligible collision probability within the validity window; e.g., >=96 bits of pseudorandom data or a version 4 UUID); usable by the server for replay detection (§11.1). |
| `htm` | Required (always) | The value of the HTTP method of the request to which the JWT is attached. |
| `htu` | Required (always) | The HTTP target URI of the request to which the JWT is attached, without query and fragment parts. |
| `iat` | Required (always) | Creation timestamp of the JWT (Section 4.1.6 of RFC 7519). |
| `ath` | Conditional — MUST be present when the proof is used in conjunction with the presentation of an access token in protected resource access (§7) | Hash of the access token: base64url encoding (Section 2 of RFC 7515) of the SHA-256 [SHS] hash of the ASCII encoding of the associated access token's value. |
| `nonce` | Conditional — MUST be present when the authentication server or resource server provides a DPoP-Nonce HTTP header in a response (§§8, 9) | A recent nonce provided via the DPoP-Nonce HTTP header. |

A DPoP proof MAY contain other JOSE Header Parameters or claims as defined by extension, profile, or deployment-specific requirements.

## 3. Checking DPoP Proofs — Complete Numbered List (§4.3)

To validate a DPoP proof, the receiving server MUST ensure the following:

1. There is not more than one DPoP HTTP request header field.
2. The DPoP HTTP request header field value is a single and well-formed JWT.
3. All required claims per Section 4.2 are contained in the JWT.
4. The `typ` JOSE Header Parameter has the value `dpop+jwt`.
5. The `alg` JOSE Header Parameter indicates a registered asymmetric digital signature algorithm [IANA.JOSE.ALGS], is not `none`, is supported by the application, and is acceptable per local policy.
6. The JWT signature verifies with the public key contained in the `jwk` JOSE Header Parameter.
7. The `jwk` JOSE Header Parameter does not contain a private key.
8. The `htm` claim matches the HTTP method of the current request.
9. The `htu` claim matches the HTTP URI value for the HTTP request in which the JWT was received, ignoring any query and fragment parts.
10. If the server provided a nonce value to the client, the `nonce` claim matches the server-provided nonce value.
11. The creation time of the JWT, as determined by either the `iat` claim or a server managed timestamp via the `nonce` claim, is within an acceptable window (see §11.1).
12. If presented to a protected resource in conjunction with an access token:
    - ensure that the value of the `ath` claim equals the hash of that access token, and
    - confirm that the public key to which the access token is bound matches the public key from the DPoP proof.

Additional notes from §4.3: to reduce false negatives, servers SHOULD employ syntax-based normalization (Section 6.2.2 of RFC 3986) and scheme-based normalization (Section 6.2.3 of RFC 3986) before comparing the `htu` claim. These checks may be performed in any order.

## 4. Key-Binding Mechanism (§6)

- Confirmation claim: `cnf` (JWT Confirmation Method framework of RFC 7800).
- Confirmation method member (defined by this RFC): `jkt` — "JWK SHA-256 Thumbprint" confirmation method.
- Value: the `jkt` member MUST be the base64url encoding (as defined in RFC 7515) of the JWK SHA-256 Thumbprint (computed according to **RFC 7638**) of the DPoP public key (in JWK format) to which the access token is bound.
- Conveyance: embedded in a JWT access token under the `cnf` claim (§6.1), or as top-level `cnf`/`jkt` structure in a token introspection response (§6.2); if `token_type` is included in the introspection response it MUST be `DPoP`.
- `token_type` value in the access token response: `DPoP` (registered OAuth access token type; a `token_type` of `DPoP` MUST be included in the access token response to signal DPoP binding, §5).
- Related: the `dpop_jkt` authorization request parameter (§10) carries the same JWK Thumbprint (RFC 7638, SHA-256) value to bind the authorization code to the DPoP key.

## 5. Error Codes and HTTP Header Names Defined/Registered

Error codes (registered in the "OAuth Extensions Error" registry, §12.2; usable in token error responses and resource access error responses):

- `invalid_dpop_proof` — the DPoP proof was deemed invalid per §4.3 criteria.
- `use_dpop_nonce` — the server requires (or requires a new) nonce in the DPoP proof; accompanied by a `DPoP-Nonce` header supplying the value (§§8, 9).

HTTP header fields (registered in the HTTP Field Name Registry, §12.8; both status "permanent"):

- `DPoP` — request header carrying the DPoP proof JWT (§4.1).
- `DPoP-Nonce` — response header supplying a server-provided nonce (§§8, 9).

Also registered (not headers): HTTP authentication scheme `DPoP` (§12.4); access token type `DPoP` (§12.1); media type `application/dpop+jwt` (§12.5); JWT confirmation method `jkt` (§12.6); JWT claims `htm`, `htu`, `ath` and updated `nonce` registration (§12.7); AS metadata `dpop_signing_alg_values_supported` (§12.9); client registration metadata `dpop_bound_access_tokens` (§12.10); authorization request parameter `dpop_jkt` (§12.3).

## 6. Eight Most Load-Bearing MUST / MUST NOT Requirements (Issuing or Validating DPoP-Bound Tokens)

1. **§5** — To request a DPoP-bound access token, the client MUST provide a valid DPoP proof JWT in a DPoP header at the token endpoint (all grant types); if invalid, the AS issues an error response with `invalid_dpop_proof`. A `token_type` of `DPoP` MUST be included in the access token response to signal the binding.
2. **§5** — When an AS supporting DPoP issues a refresh token to a public client presenting a valid DPoP proof, the refresh token MUST be bound to the respective public key, and the binding MUST be validated when the refresh token is later presented; the client MUST present a DPoP proof for the same key on each refresh.
3. **§6** — Resource servers MUST be able to reliably identify whether an access token is DPoP-bound and ascertain sufficient information to verify the binding; RSs supporting DPoP MUST ensure the public key from the DPoP proof matches the one bound to the access token.
4. **§7 / §7.1** — Requests to DPoP-protected resources MUST include both a DPoP proof and the access token, and the proof MUST include the `ath` claim with a valid hash of that access token; the RS MUST check the proof per §4.3 and the key binding per §6, and MUST NOT grant access to the resource unless all checks are successful.
5. **§7.2** — A protected resource simultaneously supporting both DPoP and Bearer schemes MUST reject a DPoP-bound access token received as a bearer token per RFC 6750 (downgrade prevention).
6. **§11.3** — A server MUST NOT accept any DPoP proofs without the `nonce` claim when a DPoP nonce has been provided to the client (nonce downgrade prevention); per §8, if the `nonce` claim does not exactly match a recently supplied nonce, the AS MUST reject the request.
7. **§11.5 / §11.6 (with §4.2)** — Servers MUST verify that the `typ` field is `dpop+jwt` in the JWT header (prevents signed-JWT swapping), and implementers MUST ensure only secure asymmetric digital signature algorithms are used — the algorithm `none` MUST NOT be allowed.
8. **§11.1** — Servers MUST only accept DPoP proofs for a limited time after their creation (preferably a relatively brief period on the order of seconds or minutes), limiting proof replay.

Other notable MUSTs (not counted in the eight): DPoP MUST always be used in conjunction with HTTPS (§2); nonce values MUST be unpredictable and there MUST NOT be more than one DPoP-Nonce header (§8); if `dpop_bound_access_tokens` is true the AS MUST reject token requests lacking the DPoP header (§5.2); with PAR, an AS supporting PAR+DPoP MUST support both `dpop_jkt` and the DPoP header, MUST check a DPoP proof on the PAR request as per §4.3, and MUST reject mismatches between `dpop_jkt` and the DPoP proof key (§10/§10.1); the DPoP authentication scheme MUST NOT be used with Proxy-Authenticate or Proxy-Authorization (§7.1).
