## Findings (non-VERIFIED)

### F1 — AMBIGUOUS: `error` challenge parameter stated as unconditional SHOULD (extraction line 120)

Claim: "Challenges use 401 with `WWW-Authenticate: DPoP`; parameters include `realm` (MAY), `scope` (MAY), `error` (SHOULD, e.g. `use_dpop_nonce`, `invalid_dpop_proof`), ..."

Source (§7.1): "An error parameter ([RFC6750], Section 3) SHOULD be included to indicate the reason why the request was declined, if the request included an access token but failed authentication."

The extraction drops the condition "if the request included an access token but failed authentication", making the SHOULD read as unconditional. The spec deliberately does NOT want error info on unauthenticated challenges — §7.2: "If no authentication information has been included with the request, then the challenges SHOULD NOT include an error code or other error information, as per Section 3.1 of [RFC6750]" (and Figure 15 shows a bare challenge: "WWW-Authenticate: DPoP algs=\"ES256 PS256\""). Verdict: AMBIGUOUS — dropped condition broadens a normative SHOULD; an implementer following the extraction would emit error codes where the spec says SHOULD NOT.

### F2 — UNSUPPORTED: jti replay tracking characterized as "SHOULD-level practice" (extraction line 142)

Claim: "replay (`jti`) tracking is described as SHOULD-level practice, not an absolute requirement (§11.1)."

Source (§11.1): "servers can store the jti value of each DPoP proof for the time window in which the respective DPoP proof JWT would be accepted to prevent multiple uses of the same DPoP proof." and "When strictly enforced, such a single-use check provides a very strong protection against DPoP proof replay, but it may not always be feasible in practice". Also §4.2: "The jti can be used by the server for replay detection and prevention; see Section 11.1."

The source never states jti tracking at SHOULD level — it is presented as purely optional ("can store"). The only nearby "should" (lowercase, non-BCP-14) concerns a different point, conditional on already tracking: "a server that is tracking jti values should reject DPoP proof JWTs with unnecessarily large jti values or store only a hash thereof." The extraction's bottom line ("not an absolute requirement") is correct, but "SHOULD-level" overstates the requirement level. Verdict: UNSUPPORTED (requirement-level mischaracterization; low practical severity since it appears in the Ambiguities section and errs toward the safer posture).
