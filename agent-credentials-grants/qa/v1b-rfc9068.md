# RFC 9068 — JWT Profile for OAuth 2.0 Access Tokens (V1-B blind re-extraction)

Source: `spec-src/agent-credentials-grants/rfc9068.txt` only.

## 1. `typ` header rules

- JWT access tokens MUST include the media type `application/at+jwt` in the `typ` header parameter "to explicitly declare that the JWT represents an access token complying with this profile" (§2.1).
- Per the definition of `typ` in Section 4.1.9 of [RFC7515], it is RECOMMENDED that the `application/` prefix be omitted; therefore, the `typ` value used SHOULD be `at+jwt` (§2.1).
- The resource server MUST verify that the `typ` header value is `at+jwt` or `application/at+jwt` and reject tokens carrying any other value (§4, first validation bullet).
- Rationale: the explicit typing (in line with [RFC8725]) prevents OpenID Connect ID Tokens from being accepted as access tokens by resource servers implementing this profile (§2.1 pointer; §5).

## 3. Complete resource-server validation list (§4)

"Resource servers receiving a JWT access token MUST validate it in the following manner."

1. **`typ` header check** — The resource server MUST verify that the `typ` header value is `at+jwt` or `application/at+jwt` and reject tokens carrying any other value. (MUST)
2. **Encryption handling** — If the JWT access token is encrypted, decrypt it using the keys and algorithms that the resource server specified during registration. If encryption was negotiated with the authorization server at registration time and the incoming JWT access token is not encrypted, the resource server SHOULD reject it. (unlabeled decrypt step + SHOULD reject)
3. **Issuer match** — The issuer identifier for the authorization server (typically obtained during discovery) MUST exactly match the value of the `iss` claim. (MUST)
4. **Audience check** — The resource server MUST validate that the `aud` claim contains a resource indicator value corresponding to an identifier the resource server expects for itself. The JWT access token MUST be rejected if `aud` does not contain a resource indicator of the current resource server as a valid audience. (MUST / MUST reject)
5. **Signature validation** — The resource server MUST validate the signature of all incoming JWT access tokens according to [RFC7515] using the algorithm specified in the JWT `alg` Header Parameter. The resource server MUST reject any JWT in which the value of `alg` is `none`. The resource server MUST use the keys provided by the authorization server. (three MUSTs)
6. **Expiration check** — The current time MUST be before the time represented by the `exp` claim. Implementers MAY provide for some small leeway, usually no more than a few minutes, to account for clock skew. (MUST + MAY leeway)

Follow-on requirements in §4 (after the bullet list):

- The resource server MUST handle errors as described in Section 3.1 of [RFC6750]; in case of any failure in the validation checks listed above, the response MUST include the error code `invalid_token`. (Note: this does not prevent JWT access tokens from using authentication schemes other than "Bearer".)
- If the token includes authorization claims (§2.2.3), the resource server SHOULD use them in combination with any other contextual information available to decide whether the call is authorized.

## 4. Six most load-bearing MUST / MUST NOT requirements

1. **Signing mandatory; `none` forbidden** — JWT access tokens MUST be signed and MUST NOT use `none` as the signing algorithm (§2.1); the resource server MUST reject any JWT in which the value of `alg` is `none` (§4).
2. **Explicit typing enforced end to end** — Issuers MUST set `typ` to the `application/at+jwt` media type (§2.1), and resource servers MUST verify the `typ` header value is `at+jwt` or `application/at+jwt` and reject any other value (§4) — the anti-ID-Token-confusion backbone of the profile.
3. **RS256 baseline interop** — Authorization servers and resource servers conforming to this specification MUST include RS256 among their supported signature algorithms (§2.1).
4. **Audience restriction** — The resource server MUST validate that `aud` contains a resource indicator identifying itself and MUST reject the token otherwise (§4); to prevent cross-JWT confusion, authorization servers MUST use a distinct identifier as an `aud` claim value to uniquely identify access tokens issued by the same issuer for distinct resources (§5).
5. **No ambiguous grants; default audience mandatory** — The authorization server MUST NOT issue a JWT access token if the authorization granted by the token would be ambiguous; if the request does not include a `resource` parameter, the authorization server MUST use a default resource indicator in the `aud` claim (§3).
6. **Client opacity** — The client MUST NOT inspect the content of the access token (§6); token format may change at any time and OAuth 2.0 assumes tokens are opaque to clients.

(Also load-bearing but not in the top six: issuer exact-match MUST and `invalid_token` error-code MUST, both §4.)

## 5. Internal quirks noticed in the source

1. **Example-vs-text `typ` casing** — Figure 2's example header (§3) is `{"typ":"at+JWT","alg":"RS256","kid":"RjEwOwOA"}` with uppercase `JWT`, while §2.1 says the value SHOULD be `at+jwt` and §4 requires resource servers to verify the value is `at+jwt` or `application/at+jwt`. Taken literally, the profile's own example token would fail the profile's §4 string check (RFC 7515 treats `typ` case-insensitively, but RFC 9068's §4 text names exact lowercase values).
2. **"authorization server response" in a resource-server requirement** — §4's error-handling sentence reads "in case of any failure in the validation checks listed above, the authorization server response MUST include the error code 'invalid_token'", in a paragraph about how *the resource server* MUST handle errors; "authorization server" appears to be a slip for "resource server".
3. **Suspect citation in §2.2.3.1** — "authorization attributes that go beyond the delegated scenarios described by [RFC7519]": RFC 7519 is the JWT spec, not a description of delegation scenarios; [RFC6749] seems to have been intended.
4. **Terminology slip "authentication server"** — §2.2.1 says the claims reflect "the types and strength of authentication in the access token that the authentication server enforced"; elsewhere the document consistently says "authorization server" (the phrase itself is also awkwardly worded).
5. **Odd example timestamps** — In Figure 2, `iat` is 1618354090 (2021-04) and `exp` is 1639528912 (2021-12): an access-token lifetime of roughly eight months, unusual for an illustrative access token.
6. **Stray whitespace in Figure 2 JSON** — `"aud":   "https://rs.example.com/"` (extra spaces) and `"jti" : "..."` (space before colon); cosmetic only.
