## Findings (non-VERIFIED only)

### F1 — AMBIGUOUS (worst finding): §6 privacy MUST narrowed to a subset of tokens
- Extraction (line 107): "Tokens carrying privacy-sensitive information MUST only be transmitted over encrypted channels (e.g., TLS)"
- Source (§6): "Tokens employed in the context of the functionality described herein may contain privacy-sensitive information and, to prevent disclosure of such information to unintended parties, MUST only be transmitted over encrypted channels, such as Transport Layer Security (TLS)."
- Verdict: AMBIGUOUS. The source's MUST governs *all* tokens employed in this context (justified because they *may* contain sensitive data); the extraction conditions the MUST on the token actually carrying sensitive information. A reader could wrongly conclude that known-non-sensitive tokens are exempt from the encrypted-channel requirement. The extraction's statement is entailed by the source (so not CONTRADICTED), but the condition is narrowed.

### F2 — AMBIGUOUS: truncated quote in §4.1 drops a qualifier
- Extraction (line 60): claims inside `act` "pertain only to the identity of the actor and are not relevant to the validity of the containing JWT"
- Source (§4.1): "claims within the \"act\" claim pertain only to the identity of the actor and are not relevant to the validity of the containing JWT **in the same manner as the top-level claims**."
- Verdict: AMBIGUOUS. The quotation is cut mid-sentence without ellipsis, dropping "in the same manner as the top-level claims." Practical conclusion is unchanged (the next source sentence confirms exp/nbf/aud "are not meaningful ... and are therefore not used"), but a quoted string should not silently truncate.

### F3 — AMBIGUOUS: "Spec's nested example (Figure 6)" silently omits two members
- Extraction (lines 63–79): JSON presented as "Spec's nested example (Figure 6, §4.1)" contains only `aud`, `iss`, `sub`, nested `act`.
- Source (Figure 6, §4.1): the figure additionally contains `"exp":1443904100,` and `"nbf":1443904000,`.
- Verdict: AMBIGUOUS. The nesting structure and all shown values match exactly, but the extraction presents a trimmed JSON as the spec's figure with no elision marker.

### F4 — UNSUPPORTED: "Many implementations invert this."
- Extraction (line 110): "Many implementations invert this."
- Source: no statement anywhere about implementation behavior or common errors (checked §4.1 and the whole document).
- Verdict: UNSUPPORTED. Editorial claim about the world, not the spec, and not prefixed `Guidance — ours, not spec:`. (The preceding fact in the same bullet — outermost = current actor, most deeply nested = least recent — is VERIFIED verbatim.)

### F5 — UNSUPPORTED: "frequently misimplemented"
- Extraction (line 111): "...`invalid_request`, not `invalid_grant` (§2.2.2) — frequently misimplemented."
- Source (§2.2.2): "The value of the \"error\" parameter MUST be the \"invalid_request\" error code." Nothing about implementation frequency.
- Verdict: UNSUPPORTED for the "frequently misimplemented" tail (the error-code fact itself is VERIFIED). Same class as F4: unmarked editorial commentary.

### F6 — AMBIGUOUS: truncated quote in §1.1 composite-token discretion
- Extraction (line 117): issuing a composite token "is at the discretion of the authorization server and applicable policy"
- Source (§1.1): "When and if a composite token is issued is at the discretion of the authorization server and applicable policy **and configuration**."
- Verdict: AMBIGUOUS (trivial). Quotation drops "and configuration" without ellipsis. The substantive negative claim ("the spec never mandates that an actor_token produce an act claim") is VERIFIED — no such mandate exists anywhere in the source; A.2.1 even attributes the composite to AS policy ("Policy at the authorization server dictates that the issued token be a composite").

### F7 — AMBIGUOUS: overview overstates what is "defined" as introspection response members
- Extraction (line 6): "defines JWT claims and introspection response members (`act`, `scope`, `client_id`, `may_act`) ... (§4)"
- Source: §4.2 — "OAuth 2.0 Token Introspection [RFC7662] **already defines** the \"scope\" parameter"; §4.3 — "[RFC7662] **already defines** the \"client_id\" parameter"; §7.5 registers only `act` and `may_act` in the introspection response registry.
- Verdict: AMBIGUOUS. As JWT claims, all four are defined/registered by RFC 8693 (§7.4); as introspection response members, only `act` and `may_act` are new. The extraction's own §4.2/§4.3 lines (85–86) state this correctly; the overview lumps them.

### Note on exempt guidance line (not counted; flagged for tension, not contradiction)
- Extraction (line 120, `Guidance — ours, not spec:`): "enforce policy only on `sub` plus the outermost `act` ... this is the direct operational reading of the §4.1 MUST."
- Source (§4.1): "the consumer of a token MUST only consider the token's **top-level claims** and the party identified as the current actor" — top-level claims, plural, include `aud`, `scope`, `exp`, not just `sub`; §5 additionally suggests "The use of the \"scope\" claim ... to mitigate potential for such abuse."
- Not a contradiction (the §4.1 MUST is restrictive, not mandatory-inclusive), but a validator following the guidance literally would skip enforcing top-level `scope`/`aud`. Recommend rewording to "top-level claims plus the outermost `act`".
