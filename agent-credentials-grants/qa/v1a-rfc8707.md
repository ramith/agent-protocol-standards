## Findings (non-VERIFIED)

### Finding 1 — AMBIGUOUS (low): omission MAYs are conditioned on "when requesting authorization"; the condition is dropped
Locations: line 39 ("**Omitted parameter** (§2.1): the AS MAY process the request with no specific resource or a predefined default resource, or MAY require clients to specify resource(s) and MAY fail omitting requests with an `invalid_target` error.") and normative table rows 10–11 ("On omission, AS MAY process with no specific resource or a predefined default"; "AS MAY require clients to specify resource(s), and MAY fail omitting requests with `invalid_target`"). 4 claim instances.

Source (§2.1): "If the client omits the "resource" parameter **when requesting authorization**, the authorization server MAY process the request with no specific resource or by using a predefined default resource value.  Alternatively, the authorization server MAY require clients to specify the resource(s) they intend to access and MAY fail requests that omit the parameter with an "invalid_target" error."

Verdict: AMBIGUOUS. The MAY grants are stated only for authorization requests; §2.2 states no omission rule for token requests (token-endpoint acceptability is covered only by the "sole discretion" sentence). The extraction cites §2.1 correctly, which partially anchors the scope, but its generic wording ("Omitted parameter", "On omission") lets a reader apply these MAYs to token requests, where the spec never grants them. Not a contradiction — a dropped condition.

### Finding 2 — AMBIGUOUS (minor): JAR presented as the rule's scope rather than as an example
Location: line 25 — "In a JWT-Secured Authorization Request, a single value is a JSON string; multiple values are an array of strings (§2.1)."

Source (§2.1): "For an authorization request sent as a JSON Web Token (JWT), **such as** when using the JWT Secured Authorization Request [JWT-SAR], a single "resource" parameter value is represented as a JSON string while multiple values are represented as an array of strings."

Verdict: AMBIGUOUS. The string/array rule applies to any JWT-encoded authorization request; JAR is cited by the spec only as an example ("such as"). The extraction narrows the rule to JAR. (Also cosmetic: the spec's referenced title is "JWT Secured Authorization Request", a then-Internet-Draft [JWT-SAR], not an RFC; the extraction does not misstate this but the hyphenated name is not the source's.)

### Finding 3 — AMBIGUOUS (trivial): §3 single-resource encouragement is stated for token requests
Location: line 29 — "§3 encourages using only a single `resource` parameter: ..."

Source (§3): "Although multiple occurrences of the "resource" parameter may be included in **a token request**, using only a single "resource" parameter is encouraged."

Verdict: AMBIGUOUS. The encouragement sentence is scoped to token requests; the extraction's paragraph covers authorization and token requests jointly, generalizing the encouragement. The supporting rationale quoted (trust between parties; "an authorization server may be unwilling or unable to fulfill a token request with multiple resources") is verbatim-accurate. Trivial severity.
